# Store submission checklist: Companion Atlas (iOS and Android)

Prepared 2026-11-01 for the Capacitor 8.6 shell in `viewer-react/mobile/`. This is preparation only.
Nothing was uploaded, no store account was created, and no real signing credential was used.

Markers used below:

- **Owner**: needs the owner's account, a key, or a decision.
- **Decide**: a choice with a recommended default.
- **Unverified**: not checked on a device or against a live service.

Store rules were read from Apple's and Google's public pages on 2026-11-01. Where the two Apple pages
disagree, both are reported.

**Item 1, the sign-in form.** The only sign-in in the app is an email and password form. It appears
when a build has `VITE_MEMORY_URL` and the Memory server answers with an authentication error. The
bearer token is kept in `sessionStorage`. The app cannot create accounts or delete them; accounts are
made outside the app with `scripts/new-account.ts`.

Apple's Guideline 5.1.1(v), as read on 2026-11-01, requires in-app account deletion for apps that
support account creation. This shell does not create accounts, so the rule may not apply. This
checklist's rule is broader (any sign-in counts), so treat it as a blocker until one of these is done:

- (a) the store build has no `VITE_MEMORY_URL`, so the app opens only the bundled sample journey. This is the smallest change.
- (b) in-app deletion is reachable from the sign-in screen, backed by a delete endpoint on the Memory server.

**Item 2, minimum functionality.** Today the native layer adds a bundled sample journey that works with
no network on an offline base map, native splash and system bars, pinch-zoom, and the system photo
and video picker. Nothing else is native. Before submission, add one native capability the web app
cannot offer (for example a share sheet for scenes, saving a scene image to Photos, or offline caching
of memories), and name it in the review notes. Do not redesign the product for this.

Rules that apply:

- **Apple, upload toolchain.** Apple's upcoming-requirements page (read 2026-11-01) says uploads must
  be built with Xcode 26 or later and the iOS 26 SDK (since 28 April 2026). The deployment target must
  be iOS 13 or later (since 9 September 2026). This build uses Xcode 27.0 with the iOS 27.0 SDK and a
  15.0 target, so it meets both.
- **Apple, April 2027.** Apple's app-store submission page says that from April 2027 uploads must use
  the iOS 27 SDK. The upcoming-requirements page does not list this. Treat it as coming, and check
  again before April 2027. The build already uses the iOS 27 SDK.
- **Google Play, target API.** New apps and updates must target API 36 or higher from 31 August 2026
  (read 2026-11-01). The app targets 36, which is compliant, and no later increase had been announced
  at that date. Nothing was changed for this.
- **Build numbers.** Play rejects a reused `versionCode`, and App Store Connect rejects a reused build
  number for the same version. Because one number serves both stores, raise it for every upload.
- **`cap migrate`** rewrites `ios/debug.xcconfig`, which carries the `#include` of `version.xcconfig`.
  Check that include after running it. `cap sync` does not touch that file.

reads the position only while the app is in the foreground, keeps it in memory, and draws it on the globe.
It is never written to storage, logged, or included in a request to any server or third party. "Nearby
memories" posts local notifications only, and nothing is sent. So the device position adds no row to the
Apple or Google answers above. If that changes, change the answers with it. The code is in
`viewer-react/src/location/`; the permission strings are in `Info.plist` and `AndroidManifest.xml`.
